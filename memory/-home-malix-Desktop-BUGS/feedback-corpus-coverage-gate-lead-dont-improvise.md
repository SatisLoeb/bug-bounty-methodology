On the Injective-web blind engagement (2026-06-27) I had the web corpus (built this same session, wired as gravedigger's pattern bank, skill says literally "LEAD HERE — the killer mode" for `--methods`) and I STILL improvised the whole hunt from curl/bundles/browser — skipping the corpus entirely. The operator caught it ("tu as utilisé notre corpus web ?"). Once I actually ran it (`web-corpus-query.sh JWT-session` → `--methods info-disclosure`), the #1 payout-density class surfaced a REAL Low finding (an unrestricted Google Maps API key in the Helix bundle) that my improvisation had missed completely.

**Why this happened (root cause, not symptom):** the classic `encoded ≠ applied` (firmaudit §0.5.4). The rule was encoded in prose in a long skill → pushed out of attention under pressure. Live black-box access (curl/bundles/browser) makes improvising *feel* productive (real responses come back), so the friction that would make me reach for the corpus never hits. And no lifecycle gate checked COVERAGE (the kill-gate/preflight check finding QUALITY, never "did you run the corpus classes").

**The fix (mechanical, not "remember"):** a hard-block gate, same pattern as `firmaudit-spine.sh` — `~/arsenal/audit-lifecycle/bin/corpus-coverage-check.sh`:
- `--emit <shape[,shape2]> <workspace>` → writes `CORPUS-COVERAGE.md`, one row per top-payout-density class from `web-corpus-query.sh <shape>`, each row `[ ]`.
- `--check <workspace>` → exits non-zero (hard-block) until EVERY row is `[x]` + has a non-empty result + a non-empty executed-artifact path.

**How to apply (every web/API engagement):** the FIRST hunting action — before any bundle/black-box improvisation — is `corpus-coverage-check.sh --emit <shape> <workspace>`, then `web-corpus-query.sh --methods <class>` on each row and probe the target. `--check` gates the close: no NO-GO / no submission with an unrun row. A row left `[ ]` = a class you didn't run = the exact miss this gate exists to stop. Improvising from the bundle is allowed AFTER `--methods` on the top-2 classes, never instead of it.

**THE BACKSTOP-NOT-VERDICT RULE (operator, 2026-06-29, ultracode session — stated as a standing principle, do NOT make him repeat it):** "Le corpus est toujours le backstop de complétude, pas le verdict." **The image to keep (operator's words): the corpus is the NET under the tightrope walker, it is NOT the tightrope walker himself.** The net catches a fall (a skipped known-payout class) so a miss doesn't kill the engagement — but it does NOT perform the walk. The walk = the manual poke + the executed artifact; that is where the finding and the verdict live. Standing in the net is not walking the rope: a green coverage gate is safety insurance, never the performance, never the conclusion. The corpus / a green `--check` (every row `[x]`) certifies ONLY *which known classes I swept* — it is completeness insurance, the proof I did not skip a known-payout class. It says NOTHING about whether the surface is CLEAN or whether a candidate is a real finding. That VERDICT — GO/NO-GO, fortress-null, finding-confirmed — is owned exclusively by the EXECUTED ARTIFACT (the fork/cast/curl disconfirmer with observed output) and the manual poke, never by "the row is checked." This is the **First Maxim applied to my own gate**: a passed coverage gate is itself a GATE — it names the EXISTENCE of coverage, never that the surface HOLDS as clean. The new failure mode this rule pre-empts: the very mechanization I built (`corpus-coverage-check.sh`) tempts reading "gate green → done/clean → close" — that is "gated → moving on" wearing my own tooling. A green gate is the START gun for the verdict work, not the verdict. Order stays: manual poke FIRST (discovery, unbounded — [[feedback-apparatus-is-packaging-not-discovery]]), corpus sweep (completeness, bounded), THEN the executed artifact decides the verdict. Three distinct jobs; the corpus owns only the middle one.
