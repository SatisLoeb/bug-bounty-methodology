**META-LESSON (encode):** on a closed-B2B bounty with **no self-serve signup + no provided creds**, the authenticated surface is likely *deliberately* out of play — and **asking the program for access can trigger an explicit perimeter-only scope lock** (exactly what happened here). For future closed-B2B web targets: at intake, treat "web app bounty + no test creds + invite-only signup" as **probably perimeter-only**, confirm authenticated-testing scope intent BEFORE deep recon, and EV-gate on the *perimeter alone* (usually thin on a hardened edge). The cold hand-poke was still correct work ([[feedback-apparatus-is-packaging-not-discovery]]) — it's what proved the perimeter solid fast — but the EV gate ([[feedback-target-diet-is-the-binding-constraint]], [[ev-gate-check-program-responsiveness-not-just-severity]]) should have flagged "authenticated surface may be OOS" as a day-0 binding risk on a closed-B2B target.

**META-LESSON-2 — "a hardened perimeter bounty is not a contradiction; it's a COMPLIANCE artifact" (2026-06-29).** When a perimeter-only program looks like "nothing is reachable," do NOT assume a hidden reachable jackpot — but DO run the unauth audit by execution before conceding (the SKIP is then earned, not reflexive). A regulated fintech holding sensitive data for many enterprise customers (Rogo = MNPI for 250 banks) MUST run a bug bounty as a SOC2 / vendor-security-questionnaire checkbox; the rational posture is a deliberately narrow, hardened, small-reward perimeter program that exists for the *customers who buy them*, not because findings are expected. "Perimeter solid" + "bounty open" are consistent. The trap to avoid is BOTH (a) over-claiming "there must be a secret door" (inflation), AND (b) conceding the perimeter un-executed (lazy null). The resolution is always: execute every unauth class → if all hold, it's a compliance-driven fortress, move on with an artifact-backed null.
