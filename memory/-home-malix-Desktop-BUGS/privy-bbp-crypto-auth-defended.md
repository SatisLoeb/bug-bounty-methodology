**Executed verdict = carefully DEFENDED (NULL-COÛTEUX → RE-SOURCE):**
- Cross-user **server/TEE wallet** read+sign BFLA (`/wallets/{id}` , `/wallets/{id}/rpc`) → DEFENDED: `401 "User does not control server wallet"` / `"User is not a signer on the wallet"` (ownership+signer checks fire before body validation).
- **#1 recovery key-material BFLA** (`POST /embedded_wallets/{addr}/recovery/key_material`) → DEFENDED BY ARCHITECTURE. Modern apps use `embedded_wallet_config.mode = user-controlled-server-wallets-only` (TEE): key in Privy's TEE, recovery **Privy-managed**, endpoint returns `404 "Embedded wallet not found"` even for the OWN wallet (no user-fetchable material). `setWalletPassword` → *"User owned wallet recovery is only supported for on-device execution and this app uses TEE execution"* — the key_material surface is **legacy on-device-only**. Not a finding on TEE apps.
- **#2 custom-JWT verification confusion** → could NOT enable `custom_jwt_auth` on the free Dev app to test (not in the Authentication UI tabs; mgmt API `POST /apps/{id}` rejects `custom_jwt_auth`/`verification_key` as unrecognized keys, dedicated route unknown; PATCH/PUT=405). Privy accepts a **pasted `verification_key`** (no JWKS hosting needed) per docs — RSA keypair+JWKS+PyJWT are staged to forge alg=none/JWK-injection/RS256→HS256/aud-iss. Low-odds (docs: Privy verifies signature+expiration; security-focused). RE-OPEN if custom-JWT gets enabled on a paid/configured app.
- Only residue: `/siwe/authenticate` accepts **any `domain`** in the signed message (no origin binding) → **Low** (nonce is app-scoped so replay bounded; not submitted).

**Lessons:** (a) browser redaction false-positive-flags PUBLIC ids (Privy app_id, cuid) — retrieve via charCodes for authorized testing. (d) MCP tab-group resets frequently in long sessions — re-`tabs_context_mcp(createIfEmpty)` + re-navigate; profile session persists.
