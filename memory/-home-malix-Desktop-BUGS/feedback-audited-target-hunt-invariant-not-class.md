Operator, 2026-07-01 (Merlin, after a full session of fortress-nulls): *"on essaie de trouver des vulns dans un protocole écrit et audité par des professionnels en croyant qu'on va trouver des vulns niveau script-kiddy — tu crois que les vulns qu'on cherche à tester ne sont pas évidentes pour eux ?"*

The whole Merlin session hunted vuln CLASSES: decimals/factor conservation, double-claim/replay guards, reentrancy on the fee `.call`, txHash-namespace replay across mint paths, API IDOR, oracle staleness, two-mint double-spend. **Every one is an auditor's bread-and-butter checklist item.** On a 5-audit BTC bridge (SlowMist/Secure3/ScaleBit/Bitmap/BlockSec) + Spearbit/Hexens CDK core, testing those is testing EXACTLY what they hardened against → each "fortress-null" was **predetermined**. A fortress-null on a known class is NOT a result — it is a confirmation the audit did its job. I spent the session PROVING the auditors worked, not finding what they missed. That is re-auditing to their spec, not hunting.

**Why:** the obvious classes are the professionals' home turf; if the bug were a class-bug, N independent audits caught it. P(class-bug survives 5 audits) ≈ 0. The bug that REMAINS is by definition NOT a class they check — it is (a) a design/economic-invariant break with no CWE, (b) a cross-component/seam composition no single audit scoped (each audit covers one contract in isolation; the system invariant across them is nobody's scope), or (c) inside a component auditors cover poorly (ZK circuit constraints, the specific economic model, off-chain infra). This is the Second Maxim + darkside Door C — which I HAD encoded and still reverted from. The pull of the checklist is strong precisely because running it FEELS like thorough work and produces confident-looking "verdicts."

**How to apply (before hunting ANY audited target):** first ask *"what does THIS protocol UNIQUELY promise, and what single assumption does that promise rest on that spans components / that no per-contract audit could scope?"* Hunt THAT, not the class list. Prefer the surfaces auditors structurally CANNOT cover:
- **ZK circuit under-constraint** — e.g. Merlin's own "incorrectly proven withdrawal" is an explicit in-scope High, and NO Solidity auditor reads the circuit/prover. The one surface where "obvious to the SC auditors" simply does not apply.
- **The whole-system economic invariant** — e.g. total M-BTC == real BTC backing, conserved across BOTH mint authorities (MPC/Cobo + CDK-bridge) AND both bridges. No per-contract audit spans two accounting authorities.
- **The DAC / sequencer / forced-inclusion trust seam.**

**The PUREST archetype (operator, 2026-07-01, DeSyn/denzoBTC2 as the example):** the on-chain↔off-chain SEAM — an **on-chain SHELL** whose shares live on-chain but whose value + redemption live 100% off-chain. denzoBTC2: 420M shares on-chain, bPool = dust (0.027 enzoBTC), oracle can't price the underlying (enzoBTC), value+redemption off-chain. CertiK audited the CRP contract **in isolation** — structurally blind to whether the on-chain price/supply reflects recoverable off-chain value. The on-chain accounting is DECORATIVE; the seam (on-chain shares ↔ off-chain value) is nobody's scope. Same shape = **Upshift Clear** (shares on-chain, value deployed off-chain via operator-reported externalAssets/deployed_aum, redemption off-chain) — which is why the only live angles there were at that seam (F-2025-14333 raw-balanceOf NAV disconnected from reality, config-drift, cross-VM inconsistency, the relayer). The seam attacks a shell enables: (1) any on-chain CONSUMER of the fictional price (lending-collateral, swap, join/exit, another pool) operates on garbage → borrow/liquidate/extract against a mispriced shell; (2) on-chain mint priced by the broken oracle/dust-pool vs off-chain redemption at real value = mint-cheap/redeem-rich; (3) dust-pool pps manipulation (bPool/shares ≈ 0) exploited by any function reading it; (4) oracle-can't-price fallback (stale/zero/revert) poisons every totalAssets consumer. **Tell you've found the shell:** on-chain pool = dust while shares = huge, or the oracle can't price the underlying, or redemption is off-chain/discretionary — the on-chain contract is a facade over off-chain value.

**Trigger to STOP:** catching myself running a per-function class checklist on multi-audit code — that is the tell I'm re-deriving the audit, not attacking it. **Corollary (target-diet):** if I'm only equipped/willing to hunt classes, an audited target is the wrong diet — go fresh, or commit to the invariant/ZK level (multi-day, thinnest competition, highest ceiling — Rule 40).
