The Ammalgam uncapped-saturation-premium finding (High, executed, 8 rounds of hardening) was REJECTED by the admin on an angle never examined: the position had to drift ~120 days untouched to reach the 15-98% seize. A MEV bot harvests the saturation reset early — a `resetSaturation` seizes premium% for zero repayment, profitable the instant `premium × collateral > gas` (a fraction of a %) — and each reset REFRESHES `oldSat`, so the premium falls back to ~0 and never accumulates. Verified by execution (`StraddleReseize.t.sol`): seize #1 takes 48%, an immediate re-seize reverts `LiquidationZeroPremium` (0x6c4e919f). No catastrophic-and-profitable corner: big collateral → harvested at ~0% (per-event loss ≈ gas), small collateral → can reach a big %, but absolute ≈ gas. The finding was dead the moment a rational harvester crossed the window.

**Why:** we hardened the seize mechanics (solvency, asymmetry threshold, premium cap, borrow band, two-call attribution) for eight rounds and never modeled the actor ecosystem crossing the 120-day drift. The frozen-baseline invariant was validated only against THIRD-PARTY actions (swaps, borrows, other accounts' liquidations); we never asked whether the victim gets harvested herself during the window — which is exactly the profitable action. "single-shot / re-registers the victim" was asserted from the NatSpec, never executed as an immediate-re-seize test.

**How to apply (encoded as tell [T-r6] in the carry-the-tell protocol + the live-template):** for ANY finding whose loss requires a position to remain in an intermediate/accumulating state for a duration (a drift, a pending epoch, an unclaimed reward, a stale price band, a growing debt), the reset/re-trigger test IS your first executed PoC, never paper reasoning: call the profitable third-party action, RE-call it same block, and READ the accumulator on-chain. The trap that made this survive 8 rounds: your finding's own thesis asserts the accumulator is frozen ("oldSat gelé / baseline frozen") — reasoning FROM that belief concludes "no reset → survives" (the wrong branch); only EXECUTING the double-liquidation revealed resetSaturation refreshes oldSat. Your frozen-baseline belief is precisely what you attack by execution (Maxim 2: understanding the code = agreeing with the dev = blindness). Three honest outcomes, and the gate KILLS only on PROOF of a permissionless-AND-profitable resetter — proven absence is a SURVIVE, "long window" is never death-by-default: (0) no permissionless-profitable actor (reset admin-only, epoch gated, intervention unprofitable to the threshold, one-shot) → the untouched window is REAL, the finding stands as-is, do not contort it into a loop-drain; (a) actor present + its action RESETS your precondition → reachability-null; (b) actor present + it does NOT reset → the repeated third-party action BECOMES your exploit (single-tx loop-drain). "No MEV bots are watching" is not a defense (an admin names it verbatim). The profitability + branch-(b) judgement lives in the money-path/adverse-actor pass (CP7), the reachability KILL in CP6.
