# CLAUDE Rules — Mandatory Gates (SCRIPT-ENCODED)

These 4 rules describe the mechanical gates enforced by the audit-lifecycle scripts. The full text here is the **specification** of behavior; the gates themselves are in `~/arsenal/audit-lifecycle/bin/`.

**The scripts are the source of truth.** If this document drifts from the script behavior, the script wins. The purpose of this document is human reference.

Auto-loaded fallback behavior in `CLAUDE.md` references D7/D8/D0-init/D0-commit by short-form; read this file for the full rationale.

36. **MANDATORY — Chain Proof Gate before submission of any auth/credential/signature finding.** This rule applies to every finding in the class **auth-bypass / hardcoded-credential / signature-forge / JWT-token / session-hijack / IDOR-write / password-reset / account-binding**. Before submitting, run `CHAIN-PROOF-GATE.md` and grep the draft for hedge phrases. The hedge scan one-liner:
    ```bash
    grep -nE "I did not test|I deliberately did not|inferred from|would access|would authenticate|would receive|deliberately not executed|not executed because|strongly indicates|architectural analysis suggests|documented .* protocol, not from testing|not confirmed whether|I stopped at|I did not attempt|the final link .* is inferred|not tested against|could not verify|assumed to be accepted" "$DRAFT"
    ```
    Any match = chain incomplete. Two options: (a) run Stage 2 of `CHAIN-PROOF-GATE.md` to find an ethical variant of the test (forge with fictitious external_id, use our own account, use two controlled accounts, target a file we created, hit metadata-only enumeration endpoints) and produce a concrete HTTP response with server-side acceptance artifact — OR — (b) downgrade severity to reflect missing impact and remove all hedge phrases claiming higher impact. **D7 in `PREFLIGHT-CHECK.md` is gating** — a failing D7 blocks submission regardless of the total score. **Why this rule exists:** the memory `feedback_auth_bypass_needs_impact.md` existed before 2026-04-13 and did not fire because it had no mechanical trigger. On the same day, Phemex R2 was marked Informative for submitting without acceptance proof (2 rep, $0), and WEEX-002 was about to be submitted with `I deliberately did not present the forged JWT to Zendesk Messenger` until a one-line question from the hunter caught the gap. Ethical acceptance test with fictitious external_id returned HTTP 200 + `authenticated:true` + permanent appUser creation. Severity jumped Medium/Informative → Critical. The reflex question "on a pas confirmé que le jwt est accepté ?" is what this rule encodes as a mechanical check so it fires every time, not just when remembered. **For smart-contract findings, this rule does not apply** — the forge-test PoC that asserts a state delta on mainnet fork is already the chain proof. For every other class touching auth/credential/signature/session/token on the web/API surface, this gate is mandatory.

37. **MANDATORY — Weight Card before submission of any non-Informational finding.** This rule applies to every finding claiming severity ≥ Low with a dollar impact. Before submitting, populate the Weight Card template in `REPORT-STANDARD.md` (section "Weight Accounting"). The hard gate is **at least one numerical anchor**: either W1 (computed dollar loss with formula and inputs from on-chain reads, API counts, or documented limits) OR W5 (≥1 paid precedent from H1/C4/Cantina/Sherlock with a dollar figure). Both slots cannot be qualitative. **DoS alternative** counts as W1 numerical anchor if downtime × req/s × affected users is measured from a reproducible PoC (downtime must be measured or extrapolated from the PoC, not asserted). An unpaid "related H1 #xxx" does not satisfy W5 — only paid references with dollar amounts count. Dashboard slots W2 (stakeholder map), W3 (reversibility audit), W4 (live conditions proof) are optional but their absence surfaces argumentation weakness pre-submission. **D8 has two sub-gates — BOTH must pass:** (8a) **Numerical anchor** — `grep -nE "could drain|could extract|could potentially|significant funds|substantial losses|large number of users|many users|many accounts|estimated to|potentially affects|at risk|exposes users to|attacker could extract|could lead to|may result in|would enable loss of|all users|all deposits|all funds|widespread impact|catastrophic|devastating|severe financial damage|impact is significant" "$DRAFT"` — each match must be paired with a specific number in the same section. The test: replace "significant funds" with "$3.47" in the draft — if the sentence becomes absurd, the number is doing the work of the argument and must be real. (8b) **Live conditions match** (mandatory IFF finding claims TVL-at-risk or N-contracts-affected) — W4 must contain `cast call` readback for EVERY contract named in the severity claim, at a specific block, and the readback must support the quantitative claim. If the draft says "6 wrappers vulnerable" and on-chain shows 5/6 empty, 8b fails. 8b N/A for access control bypass, signature forge, pure logic bugs, state-delta forge-tests with asserted $ loss, pure info disclosure. **D8 in `PREFLIGHT-CHECK.md` is gating** — D8 fail = submission blocked at claimed severity. Use `~/arsenal/tools/precedent-scan.sh <class>` to populate W5 fast — it emits a copy-paste-ready markdown block matching the REPORT-STANDARD Weight Accounting W5 table format exactly, so the slot fills without reformatting friction. **Why this rule exists:** Phemex R2 (submitted 2026-04-10, marked Informative 2026-04-13) had a proven chain and would have passed D7, but the draft said "I have not confirmed whether this enables profitable extraction via margin manipulation, because doing so would require opening leveraged positions with real capital" — weight was narrated, not computed. Rule #15 (honest impact quantification) existed but fired reactively post-oversell. Weight Card forces computation proactively, before the draft leaves the workspace. Chain Proof Gate (rule #36) answers "does the exploit execute?". Weight Card (rule #37) answers "given it executes, is it profitable for whom, irreversibly, and market-priced at what, at the current deployment state?". Both gates are complementary and catch distinct failure modes. **Reserve F-003 Convex freeze (2026-04-13 gate test)** added D8b: the draft passed D7 grep + D8a grep + 11/11 forge tests + 7 precedent rows, then on-chain `cast call totalSupply()` on the 6 named ConvexStakingWrappers revealed 5/6 empty and 1/6 with only CVX (unfailable) as its extra reward — a HIGH-claim with ~$0 realistic impact at current deployment. D8b (live conditions match) caught a new failure mode the grep-only D8a missed: quantitative claims that are factually wrong on-chain but not detectable by narrative phrase scanning. **For pure information disclosure findings already claimed at Informational/Low, this rule does not apply** — the severity floor already reflects the absent weight. **For smart contract findings where the forge-test PoC asserts a $ state delta on mainnet fork**, the state delta IS the implicit W1 AND W4 — the fork test is pinned to a block and reads real state. Caveat: the forge test must assert a dollar-equivalent delta (e.g., `assertEq(usdc.balanceOf(victim), 0)`), not merely an access pattern (e.g., `vm.expectRevert` on user_checkpoint). For every other finding making a TVL-scaled dollar claim, both D8a and D8b are mandatory.

38. **MANDATORY — Lifecycle init as first action of any target engagement, regardless of skill.** Before any Phase 0 work (gravedigger, mrrobbot, or manual audit), the FIRST command executed must be `~/arsenal/audit-lifecycle/bin/init-target.sh <target-name>` (optionally with `TARGET_HINTS="<classifier keywords>"` env var for better routing). This bootstraps: workspace directory structure (`findings/`, `evidence/`, `submissions/`), `ROUTING.md` with mandatory checklists per target class + blind spot warnings (ZK/MPC/rollup/AI), `PROGRESS.md` with gate stack checklist, `SEVERITY-COMMIT-template.md` at workspace root, `OUTCOMES.jsonl` initialized, `.lifecycle-status` marker file seeded. Idempotent — re-running on existing workspace updates timestamps and re-runs routing without resetting state. Skipping init is detectable: `preflight-mechanical.sh` refuses to PASS if the `init:` marker is absent, and every OUTCOMES entry records `preflight_run: true/false`. If `preflight_run: false` rate climbs past 20% over 30 days, the infrastructure is being ignored and the CLAUDE.md rule system has drifted from enforcement to decoration. **Why this rule exists:** every skill file (gravedigger SKILL.md, mrrobbot SKILL.md, security-disclosure SKILL.md) has its own Phase 0 procedure. Without a shared lifecycle entry point, the redundancy between skills produces drift: a gate added to one skill's Phase 0 doesn't fire for the other skill's entry path. Centralizing the lifecycle init means every entry converges on the same procedure. The redundancy in gate documentation across CLAUDE.md + PREFLIGHT-CHECK.md + CHAIN-PROOF-GATE.md + WEIGHT-CARD.md is by design (agents landing on one file must find the rule); the centralization of EXECUTION is equally by design (the rule runs once per target regardless of which document informed the hunter). **For smart-contract audits using forge-test PoCs, the rule still applies** — the workspace + OUTCOMES tracking is independent of the PoC methodology.

39. **MANDATORY — SEVERITY-COMMIT populated before opening the draft file, with artifact-required inputs per tier.** For every finding that passes the kill gate, the `findings/{id}-severity-commit.md` file (copied from template by `on-finding.sh`) must be filled and signed by `artifact-validator.sh` BEFORE the draft file is opened. The commit form implements the equation `severity = min(evidence_strength, chain_completeness, impact_quantified)` where each input requires a physically resolving artifact pointer to commit at a non-default tier. Defaults are L1 evidence, unverified chain, narrative impact — if no artifact is cited, the input stays at the default tier and the severity ceiling drops accordingly. Artifact-required tiers: L2 evidence requires file:line refs that resolve; L3 requires executable reproduction (Foundry test path, curl command, anchor test); L4 requires tx hash + block number + `cast call` output or fork-pinned test. `full_ethical` chain requires an HTTP response block or forge state-delta assertion. `computed_W1` requires a dated calculation block with sourced inputs. `W5_anchored` requires a pointer to a paid precedent with a dollar figure. Each non-default tier also requires a one-sentence `artifact_proves:` field tying the artifact to THE claim being made (not a class-level proof). **Why this rule exists:** rule #37 (Weight Card D8) catches narrative weight after the draft is written — the draft still has to be rewritten or downgraded, wasting the writing effort AND creating pressure to defend the inflation. Rule #39 fires before the draft exists, forcing severity commitment based on evidence I currently hold, not evidence I intend to gather during writing. HRB-001 (2026-04-14) drafted a 3000-word HIGH with GLBA/FTC framing that would have been blocked at Low-MAX by the equation: evidence=L2 (static auth bypass trace, no dynamic test), chain=partial (some links proven, some not), impact=narrative (compliance framing without specific dollar or user count). Phemex R2 similarly: evidence=L3, chain=full, impact=narrative → Medium MAX by the equation, not HIGH. The inflation to HIGH required upgrading impact to computed_W1 which required real leveraged-position capital — gate would have forced the honest downgrade at the framing stage, before 3000 words were committed. The rule is artifact-required specifically because auto-declaration under the same framing bias that produces the failures would reproduce the failures at a displaced level. The artifact must exist, be pointable, and prove THE specific claim — not a generic class of claim. `on-finding.sh` enforces the flow: copies the template, requires `artifact-validator.sh` PASS signature before the draft path opens. `preflight-mechanical.sh` re-checks the commit signature before submit (D0-commit). **For smart-contract findings with mainnet-fork forge-test PoCs that assert dollar-delta state changes**, the forge test itself serves as the L4 artifact and the implicit W1 — the severity-commit is still required but fills quickly because the artifacts pre-exist.
