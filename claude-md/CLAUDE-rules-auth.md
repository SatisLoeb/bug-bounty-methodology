# CLAUDE Rules — Auth / Credential / Token

Load on-demand when target involves JWT/OAuth/SAML/session auth, credential handling, or signature-class vulnerabilities. Referenced from main `CLAUDE.md` under "Authentication-class target rules".

19. **Null-gate / type-confusion bypass in auth layers** — When a security check is gated on `if (X != null)` where X comes from a type-narrowing operation (`toSignedJWT()`, `instanceof`, `.as::<T>()`), check if an attacker can supply a **spec-valid alternative type** that makes the narrowing return null → entire security check silently skipped while the authenticated action proceeds. CVE-2026-29000 (pac4j-jwt, CVSS 10): PlainJWT inside JWE bypasses signature verification using only the RSA public key. This generalizes to: OAuth2 token type confusion, SAML unsigned-in-encrypted, protobuf oneof confusion, deserialization instanceof bypass. **Hunt pattern**: `grep -rn "!= null.*verify\|instanceof.*verify"` — every hit is a potential null-gate.

20. **Spec-allowed-but-unexpected inputs** — Before marking auth/validation as secure, enumerate ALL input types that the protocol/spec permits (not just the expected happy path). JWT allows PlainJWT, JWS, JWE. OAuth2 allows multiple grant types. SAML allows signed and unsigned assertions. If the code only handles the expected type and skips validation for others, it's a bypass.

21. **JWK header auto-trust (RFC 8725 §2.4 violation)** — If a JWT library auto-trusts the `jwk`/`jku`/`x5c` parameter in the token header for key material, an attacker signs with their own key and embeds their public key in the header → signature verification passes with attacker-controlled claims. **Hunt pattern**: `grep -rn "jwk.*header\|header.*jwk\|jku.*fetch\|x5c.*cert\|key.*None.*header\|key.*null.*header" --include="*.py" --include="*.js" --include="*.ts" --include="*.java" --include="*.go" --include="*.rs"` — check every hit for auto-trust of header-embedded keys when the application key is None/null/missing. **Confirmed in**: Authlib <= 1.6.8 (AUTH-001, silently fixed v1.6.9). Also check: does the library fall back to header `jwk` when application key loading fails (returns None)? Internal inconsistency signal: if JWT-level API is protected but lower-level JWS/JWE API is not.

22. **DER-encoded key algorithm confusion (CVE-2024-33663 bypass)** — CVE-2024-33663 fixed algorithm confusion by detecting PEM-format keys in HMAC constructors. But DER-encoded keys are binary (no `-----BEGIN` marker) and bypass `is_pem_format()` checks entirely. Attacker obtains public key from JWKS endpoint, converts to DER, uses as HMAC secret to forge HS256 tokens. **Hunt pattern**: `grep -rn "is_pem_format\|is_ssh_key\|BEGIN.*END\|pem_format\|asymmetric.*key.*error" --include="*.py" --include="*.js" --include="*.ts" --include="*.java" --include="*.go"` — if the check only matches PEM text patterns, DER binary keys bypass it. Also check: does `algorithms` parameter default to `None`/`null` (skipping allowlist)? Does `verify_signature=False`/`verify=False` skip ALL checks including algorithm validation? **Confirmed in**: python-jose all versions (JOSE-001, unmaintained). **Safe libraries**: PyJWT 2.11+ (NoneAlgorithm.verify() always returns False), Hono 4.11.4+ (mandatory alg, header mismatch check), go-jose/v4 (mandatory allowlist), lestrrat-go/jwx v3 (caller-specified alg).
