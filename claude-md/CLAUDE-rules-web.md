# CLAUDE Rules — Web / API

Load on-demand for web application and API targets. Covers authenticated session testing, authorization consistency, and H1 hacktivity pattern scanning.

29. **MANDATORY: Authenticated session testing on every web API target** — A WAF returning 403 means "requires auth", NOT "blocked." Create a test account via normal signup, capture the Bearer token, and test EVERY route extracted from JS bundles WITH the token. The entire authenticated API surface is invisible without this step. Request Finance: 103 routes extracted including `DELETE /users/mfa`, all noted "high-value" but never tested with auth because WAF returned 403. A single authenticated curl revealed MFA deletion without re-auth (CVSS 7.6 HIGH). See gravedigger §4.12, WEB-API-CHECKLIST W8.

30. **Authorization consistency matrix for every app with elevated auth** — Map every security-critical operation (MFA management, SSO, password/email change, session revocation, account deletion) and verify each requires re-authentication or elevated scope (sudo, step-up, MFA challenge). If ANY lower-sensitivity operation requires higher authorization than a security-critical one, it's an oversight finding. Pattern: `GET /apps` requires sudo but `DELETE /users/mfa` doesn't = HIGH. Also check: can security notification types be silently disabled via user preferences API? This enables the silent ATO kill chain (suppress alerts → strip MFA → unlink SSO → zero notification to victim). References: OWASP ASVS V3.7.1, NIST SP 800-63B-4, CWE-306, CVE-2023-40260 (CVSS 9.1), CVE-2026-27946 (CVSS 8.2).

34. **MANDATORY for web/API targets: H1 hacktivity pattern scan** — Apply the detection priority matrix from `~/arsenal/methodology/H1-HUNTING-PATTERNS.md` on every web/API engagement. 13 categories, 60+ patterns extracted from 2,500+ disclosed HackerOne reports. Key meta-patterns: M-H1-001 (inconsistent auth across interfaces -- REST vs GraphQL vs WebSocket), M-H1-002 (destructive ops have weaker auth than read ops), M-H1-003 (race windows in state transitions), M-H1-004 (user-controlled URLs = SSRF candidates), M-H1-007 (session tokens before auth complete = MFA bypass), M-H1-008 (same resource different route different auth), M-H1-010 (always chain -- IDOR read=$1K vs IDOR->ATO=$12K). ROI data in `~/arsenal/methodology/H1-STATISTICS.md`: IDOR+auth bypass outpay XSS 3:1. AI/LLM vulns +540% YoY (P-H1-100, P-H1-101).

43. **MANDATORY before routing/auditing any npm or GitHub package: NPM SOURCE ≠ DEPLOYED CODE, and a PUBLIC FORK ≠ a CUSTOM DEVIATION (the /orca Exodus test, 2026-06-21).** Finding a package's source on npm/GitHub is NOT finding the DEPLOYED code, and "scoped to `@org/`" is NOT "custom and un-ploughed." Classify EVERY source package on two axes before pointing depth at it — each axis changes the route, and getting it wrong wastes days:
    - **(a) DEPLOYED code vs SDK/library UPSTREAM of it (Rule 5 applied to packages).** A package named `@org/headless` / `@org/sdk` / `@org/core` / `*-kit` is almost always an ABSTRACTION the real client wires a topology AROUND — auditing it tells you what the SDK *would* do, never what the deployed Desktop/Mobile/contract *does*. Read the npm `description`/repo: if it self-describes as "SDK" / "headless" / "library," the DEPLOYED artifact is elsewhere (the Electron `.asar` in the real desktop build, the mobile binary, the on-chain address) — route the deep audit at the DEPLOYED artifact and use the SDK source only as the scan-free MAP to its request/RPC shapes. (Exodus: `@exodus/headless` = "The headless Exodus wallet SDK," NOT "the Desktop/Mobile client source" the plan claimed; the deployed client is the asar that wires this SDK.) This is the package-level form of "source says what the code WOULD do; only RE of the deployed layer says what the running system DOES."
    - **(b) CUSTOM-to-the-org vs PUBLIC fork of a STANDARD.** Before cadre-ing a package as a "custom-between-standards, un-ploughed deviation" (the darkside Door C vein), check the npm description + repo: does it implement/fork a KNOWN STANDARD or mainstream lib (JSON-Schema drafts, ajv/is-my-json-valid, a standard crypto primitive, a serialization format)? If YES it is NOT a deviation-from-canonical — it is a public CONFORMANCE implementation, so (i) **Door C is the WRONG tool** (Door C diffs against the canonical form to find an UNWRITTEN invariant; a conformance impl IMPLEMENTS the canonical form, so the bug is a standard-CONFORMANCE/soundness defect — an input the spec rejects that the impl accepts → route **darkside Door A + a DIFFERENTIAL fuzz against the reference lib**, never Door C); and (ii) it carries **PUBLIC dup-risk + a GHSA-upstream angle** (other projects use it, other hunters read it) — it is NOT "un-ploughed," do not sell it as such. (Exodus: `@exodus/schemasafe` = a public MIT fork supporting JSON-Schema drafts 04-2020-12 = a conformance impl → Door A + differential-fuzz-vs-ajv + a dup/GHSA note, NOT Door C "un-ploughed.")
    The meta-lesson: a routing plan (e.g. from `/orca`) is an agent output — VERIFY its load-bearing facts (read the npm description, the repo) BEFORE "go," exactly like any agent claim.
